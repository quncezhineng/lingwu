# PRD：任务目标提醒

> 版本：v0.1 | 日期：2026-11-06 | 状态：Draft | 范围：任务中心内的目标、任务与提醒重组
>
> 一句话定义：把「目标、任务、条件提醒、通知」从四份平行数据，组织成一条能直接回答「现在该做什么、什么时候会再提醒我、最近发生了什么」的**目标轨道**。

---

## 1. 摘要

当前任务中心已经完成「任务」与「目标 + 提醒」的一级收拢，但用户进入「追踪」后，看到的仍是一个目标和提醒混排的平铺列表。目标只有里程碑进度，提醒只有检查周期，任务只有执行状态；三者没有在同一张卡片里形成「下一步」。

本方案不建议新增第三套“目标提醒”实体，也不新增一级导航。推荐做三件事：

1. 在任务中心顶部增加 **「接下来」**：只展示需要用户行动、或即将发生的最多 3 项，跨任务、提醒和目标统一排序。
2. 把「提醒」页改造成 **「目标轨道」**：以目标为父级，组合同一目标下的里程碑、任务、关联提醒和最近变化；无目标归属的提醒进入「独立提醒」。
3. 允许条件提醒通过可选 `goalId` / `milestoneId` 关联目标，复用现有 `Monitor -> AgentTask -> AgentNotification` 链路，不新增数据表或业务路由。

最终体验不是“又多了一个提醒入口”，而是“打开任务中心，第一眼就知道哪一件事最值得处理”。

## 2. 背景与证据

### 2.1 当前实现

| 能力 | 当前代码事实 | 用户看到的形态 |
| --- | --- | --- |
| 任务 | `AgentTask` 已有 `goalId`、`milestoneId`，由服务端耐久执行 | 按状态筛选的任务卡片 |
| 目标 | `Goal` 有里程碑，任务可挂到目标/里程碑 | 目标行 + 里程碑进度 |
| 条件提醒 | `Monitor` 绑定一个监控任务，按页面、价格或文本条件周期检查 | 提醒行 + 开关 + 编辑 |
| 通知 | `AgentNotification` 可关联 `taskId` | 扁平通知列表 |
| 任务中心 | `TaskHubScreen` 分为「任务 / 定时」两个一级页签；`GoalsScreen` 在视图层平铺 Goal 与 Monitor | 类型优先，关系不显性 |

### 2.2 用户问题

1. **「定时」这个名称不准确。** 徽标数量同时包含目标和提醒，但目标并不一定有定时行为，用户无法从名称推断内容。
2. **目标和提醒看起来一样，实际不是一回事。** 两者都使用卡片列表，但目标表达结果与里程碑，提醒表达周期性外部检查；平铺后语义被压扁。
3. **用户需要自己做关联。** 一个目标下有任务、有一个每周复盘提醒；用户必须分别点开目标、任务和提醒，才能拼出当前状态。
4. **任务卡片缺少目标上下文。** 用户看到「准备回复」「核对估值」，但不知道它服务于哪个目标。
5. **通知是扁平的。** 用户看到一条提醒结果，却看不到它属于哪个目标、哪个承诺，也判断不出处理顺序。
6. **目标没有“下一步”。** 没有里程碑或没有活跃任务的目标，只显示进度 `0/0`，没有明确动作引导。

### 2.3 机会点

用户真正的问题不是“提醒不够多”，而是“在一堆持续工作中，不知道先看哪一个”。因此本功能的竞争点应该是**排序与上下文**，不是通知数量。

## 3. 产品目标

### 3.1 目标

- 用户进入任务中心后，10 秒内能判断当前最需要处理的一件事。
- 目标、任务和提醒的关系无需跨页面拼装即可看懂。
- 新增提醒可以自然归属于目标，但现有独立提醒不需要迁移。
- 不增加新的数据表、服务端聚合接口或一级导航。

### 3.2 成功指标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 「接下来」首项点击率 | ≥ 35% | 进入任务中心后点击首项的比例 |
| 待确认任务处理时长 | 降低 30% | 从任务进入 `waiting_input` / `waiting_approval` 到用户处理 |
| 目标关联提醒占比 | 新提醒中 ≥ 25% | 验证“目标轨道”是否真的被使用 |
| 目标页下一步动作点击率 | ≥ 20% | 目标卡片中「继续任务」或「制定下一步」的点击 |
| 通知深层打开率 | 提升 15% | 从通知打开对应任务或提醒的比例 |
| 通知总量 | 不增加 | 聚合展示不能演变为更多推送 |

### 3.3 非目标

- 不做甘特图、日历排期或依赖关系图；当前目标没有可靠截止时间。
- 不新增「目标提醒」数据表，不复制一套调度器。
- 不把模型生成的时间当成截止时间，不伪造“逾期”。
- 不在本期接设备推送，仍以站内通知为主。
- 不改变任务、目标、提醒的所有权与权限边界。
- 不把已完成目标永久置顶，避免历史完成项制造噪音。

### 3.4 产品原则

1. **确定性优先。** 排序由可解释规则完成，不用模型猜测优先级。
2. **行动优先于类型。** 先回答“要做什么”，再回答“它是什么类型”。
3. **不折叠领域对象。** `Goal`、`AgentTask`、`Monitor` 仍在数据层独立，只在视图层建立关系。
4. **少而可信。** 最多展示 3 个“接下来”项；没有需要行动的事就明确说没有。
5. **保留旧数据。** 没有 `goalId` 的任务和提醒继续作为独立项显示。

## 4. 核心概念

### 4.1 领域关系

```text
Goal（为什么做 / 要达成什么）
  ├── Milestone（目标内部的阶段）
  ├── AgentTask（现在执行的工作，可挂 goalId + milestoneId）
  └── Monitor（周期性观察外部条件）
        └── AgentTask（每次检查的执行记录）
              └── AgentNotification（回执 / 变化 / 需要用户处理）
```

### 4.2 提醒的边界

- **提醒仍然是 `Monitor`**：它表示“按节奏检查一个公开页面/价格/文本条件”，不是任意时间点的待办。
- **任务回执仍然是 `AgentNotification`**：任务完成、失败、等待输入和等待审批继续走现有通知链路。
- **目标轨道是视图模型**：不是数据库实体，不参与任务执行，不自行发通知。

这样可以避免再引入一个“目标提醒”对象，与现有的 `Monitor`、定时任务和通知产生三重语义。

### 4.3 推荐的用户心智

> 目标是我要去的方向；任务是我正在做的事；提醒是灵悟替我在某个节奏上继续看；接下来是我现在需要处理的事。

## 5. 方案比较

| 方案 | 描述 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- | --- |
| A. 新增「目标」第三页签 | 任务 / 提醒 / 目标三个一级页签 | 分类直观 | 信息继续分裂；目标与提醒的关系仍不可见；导航更重 | 否 |
| B. 目标详情做成项目看板 / 甘特图 | 按时间展示里程碑、任务、提醒 | 可视化强 | 当前缺少可靠截止时间；维护成本高；不符合轻量个人投研产品 | 否 |
| C. 「接下来」+「目标轨道」 | 顶部跨类型行动摘要，追踪页按目标聚合 | 直接解决优先级和上下文；复用现有数据 | 需要新增纯视图投影和少量目标关联字段 | **推荐** |
| D. 仅优化对话内摘要 | 通过 Agent 汇报当前任务与提醒 | 实现轻 | 用户仍需进入页面处理；无法替代工作台 | 作为补充，不作为主方案 |

### 5.1 决策

采用 **C**。P0 只做“视图聚合 + 提醒可关联目标”，不改变任务执行模型。

## 6. 信息架构与呈现

### 6.1 页面结构

```text
任务中心
├── 接下来（最多 3 项，跨任务 / 提醒 / 目标）
├── 一级页签：任务 | 追踪
│   ├── 任务：沿用现有状态筛选
│   └── 追踪：
│       ├── 关注中的目标（按目标聚合）
│       ├── 独立提醒
│       └── 已完成 / 已暂停（可折叠）
└── 新建：建立目标 / 设置提醒 / 委派任务
```

「接下来」不是第三个页签，而是任务中心顶部的常驻摘要；没有可展示项时整块收起。

```text
┌──────────────────────────┐
│ 接下来 2                 │
│ 需要补充信息             │
│ 算力产业链研究           │
│ 缺目标公司代码    [去补充]│
│                          │
│ 今天 15:30 自选公告      │
│ 1 小时 20 分钟后  [查看] │
├──────────────────────────┤
│ [任务 18]     [追踪 6]   │
│                          │
│ 关注中的目标             │
│ 算力产业链研究   2/4     │
│ 下一步：核对目标公司估值 │
│ 每周五 15:30 · 下次 11/13│
│ [继续任务]               │
└──────────────────────────┘
```

移动端「接下来」默认最多 2 项，目标卡片默认只展开「下一步」，提醒与最近变化按需展开。

### 6.4 「接下来」排序规则

所有条目由 `AgentWorkspace` 本地派生，按以下规则排序。相同优先级按时间升序，再按 ID 稳定排序。

| 优先级 | 条件 | 展示动作 | 点击去向 |
| ---: | --- | --- | --- |
| 100 | 任务 `waiting_input` | 去补充 | 任务详情并定位输入区 |
| 95 | 任务 `waiting_approval` | 去确认 | 任务详情 / 审批流 |
| 80 | 任务 `failed` | 查看并重试 | 任务详情 |
| 75 | 提醒暂停且存在错误 | 修复提醒 | 提醒详情 |
| 60 | 提醒 `nextCheckAt` 在未来 24 小时内 | 查看提醒 | 提醒详情 |
| 40 | 活跃目标没有下一步任务、没有关联提醒、且没有未完成里程碑 | 制定下一步 | 目标详情 |
| 20 | 目标包含多个未完成里程碑但近期无活跃任务 | 查看目标 | 目标详情 |

补充规则：

- 仅展示前 3 条；同一目标最多占 2 条，避免一个目标淹没其他工作。
- 已停止的提醒、已完成/已取消任务、已完成目标不进入「接下来」。
- 普通运行中的任务不进入「接下来」，只在「任务」页和目标卡片中出现。
- 不展示任务错误原文、内部工具名、路径或模型诊断信息；沿用 `presentTask` 的脱敏原则。

### 6.5 目标轨道卡片

每张卡片固定四层信息，顺序不能变：

1. **身份层**：目标标题、状态、里程碑进度。
2. **下一步**：只展示一个最高优先级动作；没有则显示「为这个目标定一个下一步」。
3. **节奏**：最多展示 2 条关联提醒，显示“下一次什么时候、检查什么”；更多时显示「另有 N 条」。
4. **最近变化**：最近一次任务结果、提醒告警或里程碑完成，最多一行。

主操作：

- 有待处理任务：`继续任务`
- 无下一步：`制定下一步`
- 有暂停/异常：`查看并处理`
- 次级操作：`查看目标`、`调整提醒`

目标暂停时，卡片整体降级为中性色，不再显示为“进行中”；关联提醒若因任务暂停而无法执行，应显示「随目标暂停」，不能显示“正常监控中”。

### 6.6 独立提醒

- 未关联目标的提醒保留在第一阶段功能中，放在「独立提醒」分组。
- 现有提醒不批量迁移，不猜测目标归属。
- P1 提供“关联到目标”操作，允许用户主动选择；没有选择就继续独立展示。
- 已停止的提醒不出现在列表，但历史通知仍然保留。

### 6.7 通知分组

P0 不改变通知数据；P1 在通知抽屉中按目标分组：

```text
算力产业链研究
  · 每周自选回顾发现了 2 条公告变化
  · 需要你补充目标公司代码

独立
  · 恒生电子价格提醒已触发
```

分组依据：`notification.taskId -> task.goalId -> goal`。任务不存在或目标已删除时回退为「独立」，不隐藏通知。

## 7. 功能需求

### 7.1 P0：视图聚合（必须）

#### R1. 新增统一追踪视图模型

提供纯函数：

```ts
buildTrackingView(workspace: AgentWorkspace, now: Date): TrackingView
```

输出：

```ts
type TrackingView = {
  nextUp: AttentionItem[];
  goalTracks: GoalTrack[];
  standaloneReminders: Monitor[];
  counts: {
    tasks: number;
    tracking: number;
    attention: number;
  };
};
```

约束：

- 不读取网络，不调用模型。
- 不修改输入对象。
- 对 `now` 显式注入，方便测试时区和 24 小时窗口。
- 所有日期比较使用 `Asia/Shanghai`，与现有提醒调度语义保持一致。

#### R2. 「接下来」摘要

- 位于任务中心页签上方。
- 最多 3 条，同一目标最多 2 条。
- 有 1 条时展示为单卡，2–3 条时展示为紧凑列表。
- 没有条目时整块不渲染，不出现“空提醒”占位。
- 每条包含：类型标签、标题、原因、动作按钮。
- 点击动作后先更新对应通知为已读（若由通知派生），再进入详情。

#### R3. 目标轨道聚合

- 将带 `goalId` 的任务与提醒渲染在目标卡片内。
- 任务与提醒仍可打开各自现有详情，不复制编辑能力。
- 没有目标的提醒进入「独立提醒」。
- 目标排序：需处理 > 最近活跃 > 创建时间倒序。
- 3 秒轮询只刷新内容，不能因 `lastCheckedAt` 更新造成列表跳动；沿用现有“成员集合不变则保持顺序”的做法。

#### R4. 提醒携带目标上下文

新增可选字段：

```ts
interface Monitor {
  // ...现有字段
  goalId?: string;
  milestoneId?: string;
}
```

- P0 从目标详情或目标卡片新建提醒时，自动带入 `goalId`；可以选择具体里程碑。
- 服务端校验目标属于当前 owner，里程碑属于该目标。
- 创建提醒的监控任务时，将 `goalId` / `milestoneId` 复制到 `AgentTask`。
- P1 允许已有提醒关联、改绑或解除目标；更新时同步修改执行任务的目标上下文。
- 没有 `goalId` 的旧数据完全兼容。

#### R5. 命名与计数

- 一级页签「定时」更名为「追踪」。
- 追踪内筛选改为「全部 / 目标 / 提醒」，其中“提醒”包含独立提醒和目标关联提醒。
- 页签计数只表达条目数，不表达紧急度；紧急度只由「接下来」表达。
- 已完成目标默认折叠到「已完成」，不计入“需要关注”的语义，但可以保留在总条目数中。

#### R6. 目标上下文进入任务卡片

- 任务卡片增加一行目标标签，例如「算力产业链研究 · 核对估值」。
- 标签可点击，打开目标详情。
- 任务详情顶部也显示目标与里程碑。
- 目标被暂停或完成时，在任务卡片上用文字说明，不改变任务本身状态。

### 7.2 P1：收件箱与关联管理（建议）

- 通知抽屉按目标分组。
- 支持将现有独立提醒关联到目标、解除关联或改绑。
- 目标轨道增加「最近 7 天」活动摘要：完成里程碑、任务回执、提醒告警。
- 目标完成后，关联提醒进入「已完成目标的提醒」折叠区，由用户决定是否暂停。
- 为每个目标提供每日最多一条的站内摘要，不新增逐条提醒推送。

### 7.3 P2：后续能力（不在本期）

- 设备推送。
- “超过 N 天未推进”自动提醒。
- 智能建议提醒节奏。
- 延后提醒 / 静默时段。
- 日历视图和多目标依赖关系。

## 8. 数据与技术方案

### 8.1 数据模型变更

只增加可选字段，不新增表：

```ts
// packages/domain/src/agent.ts
interface Monitor {
  // ...现有字段
  goalId?: string;
  milestoneId?: string;
}

const monitorInputSchema = z.object({
  // ...现有字段
  goalId: z.string().optional(),
  milestoneId: z.string().optional(),
});
```

`AgentTask` 已有 `goalId` / `milestoneId`，`AgentNotification` 已有 `taskId`，均不修改。

### 8.2 服务端规则

在 `createMonitor` / `updateMonitor` 中：

1. 若传入 `goalId`，读取并验证目标属于当前 owner。
2. 若传入 `milestoneId`，要求同时有 `goalId`，且里程碑存在。
3. 创建监控任务时复制目标上下文。
4. P1 更新提醒目标上下文时，同时更新执行任务的 `goalId` / `milestoneId`。
5. 不新增 `/tracking` 或 `/attention` 接口；客户端继续使用 `/api/agent` 快照。

实现时注意 `compareAndSwap` 的 JSON 合并语义：取消关联需要显式清空字段，不能只依赖 `undefined`。P0 只支持在创建提醒时关联；P1 再实现已有提醒的关联、改绑与解除，避免引入半完成的状态迁移。

### 8.3 前端分层

```text
AgentWorkspace（现有 3 秒轮询）
        │
        ▼
tracking-view.ts（纯函数：排序、分组、下一步、时间窗口）
        │
        ├── NextUpStrip
        ├── GoalTrackCard
        ├── StandaloneReminderRow
        └── NotificationGroup（P1）
        │
        ▼
现有 TaskDetail / GoalCard / MonitorCard / MonitorForm
```

建议新增：

- `apps/mobile/src/tracking-view.ts`：只做数据投影，易单测，不依赖 React。
- `apps/mobile/src/tracking-screen.tsx`：目标轨道与「接下来」组件。

保持：

- `task-hub.tsx` 继续做页面编排，不承载排序规则。
- `task-presentation.ts` 继续负责任务脱敏展示，不把目标逻辑塞进去。
- `agent-ui.tsx` 的表单和详情组件复用，不在其中新增聚合逻辑。

如果 `agent-ui.tsx` 继续膨胀，P1 再把 `GoalsScreen` 的整体 UI 迁到 `tracking-screen.tsx`；P0 不做大迁移，降低回归风险。

### 8.4 视图模型建议

```ts
type Attention = {
  id: string;
  source: "task" | "monitor" | "goal";
  priority: 20 | 40 | 60 | 75 | 80 | 95 | 100;
  title: string;
  reason: string;
  actionLabel: string;
  taskId?: string;
  monitorId?: string;
  goalId?: string;
};

type GoalTrack = {
  goal: Goal;
  nextAction?: Attention;
  reminders: Monitor[];
  recentActivity?: {
    at: string;
    text: string;
    taskId?: string;
  };
  activityAt: string;
};
```

`activityAt` 取以下最大值：

- `goal.createdAt`
- 该目标下任务的最大 `updatedAt`
- 该目标关联提醒的最大 `lastCheckedAt`

当前 `Goal` 没有 `updatedAt`，因此 P0 不展示“目标逾期”或精确的“未推进天数”。需要该能力时，先补 `Goal.updatedAt`，再启用文案。

### 8.5 关键推导

目标“下一步”按下列顺序取第一个：

1. 目标下 `waiting_input` 的任务。
2. 目标下 `waiting_approval` 的任务。
3. 目标下 `failed` 的任务。
4. 目标下活跃的 `queued` / `running` / `scheduled` 任务。
5. 目标关联提醒中最接近 `nextCheckAt` 的活跃提醒。
6. 第一个未完成里程碑。
7. 无下一步，生成“制定下一步”动作。

同一目标最多只把一条任务放入「接下来」；其余任务留在目标卡片或任务页。

### 8.6 兼容性

- 无 `goalId` 的旧任务继续在任务页显示，不强制迁移。
- 无 `goalId` 的旧提醒继续在独立提醒显示。
- 旧通知继续按扁平列表显示；P1 分组失败时回退到原列表。
- 已停止的提醒、已完成目标、旧监控任务的 `TASK_SETUP_REQUIRED` 状态均不伪装成正常。

## 9. 交互细节

### 9.1 进入与返回

- 从底部「动态」或侧栏「任务」进入任务中心，默认停留在上次页签；首次进入为「追踪」。
- 从通知点击目标轨道条目，关闭通知抽屉后直接打开对应详情，返回时回到任务中心原位置。
- 从目标详情创建提醒，保存后返回目标详情，不跳回列表顶部。

### 9.2 行动按钮

- 按钮文案使用动作而不是类型：`去补充`、`去确认`、`继续任务`、`制定下一步`、`查看提醒`。
- 同一行最多两个按钮；次级操作收进更多菜单。
- 不把整张包含多个按钮的卡片设为一个可点击按钮，避免无障碍角色冲突。

### 9.3 状态与空态

| 场景 | 文案方向 |
| --- | --- |
| 无「接下来」 | 不渲染整块，避免“没有提醒”的焦虑 |
| 无目标 | 「还没有目标」「扎实的投资，都始于扎实的研究。」保留现有引导 |
| 无提醒 | 「还没有提醒」「让灵悟按节奏替你继续看。」 |
| 目标无下一步 | 「先定一个下一步」+ 目标详情操作 |
| 提醒因目标暂停 | 「随目标暂停」 |
| 目标已完成 | 「目标已完成」+ 折叠区 |

### 9.4 移动端与无障碍

- 390px 视口下不横向滚动；长标题最多 2 行。
- 时间、优先级、未读状态均有文本，不只依赖颜色。
- `accessibilityLabel` 包含目标名称和动作，例如「为算力产业链研究补充目标公司代码」。
- 点击区域不小于 44×44。
- 减少动效时禁用列表排序动画。

## 11. 验收标准

### AC1：接下来聚合

- **Given** 工作区有一个 `waiting_input` 任务、一个 1 小时后执行的提醒和一个普通运行中任务
- **When** 用户进入任务中心
- **Then** 「接下来」显示前两项，普通运行中任务不出现
- **And** 首项动作是「去补充」，点击后打开对应任务

### AC2：目标轨道

- **Given** 一个目标有 2 个未完成里程碑、1 个挂在该目标下的任务和 1 条关联提醒
- **When** 用户打开「追踪」
- **Then** 这三者出现在同一张目标卡片中
- **And** 卡片只显示一个最高优先级的“下一步”
- **And** 没有 `goalId` 的提醒出现在「独立提醒」

### AC3：关联持久化

- **Given** 用户从目标详情创建提醒并选择里程碑
- **When** 保存并刷新页面
- **Then** 提醒保留 `goalId` / `milestoneId`
- **And** 其监控任务带有相同的目标上下文
- **And** 该提醒不再出现在独立提醒分组

### AC4：安全与隔离

- **Given** 用户 A 尝试把提醒关联到用户 B 的目标
- **When** 调用创建或更新接口
- **Then** 服务端返回 404，不泄露目标是否存在

### AC5：兼容旧数据

- **Given** 工作区只有旧任务和旧提醒，均无 `goalId`
- **When** 用户打开任务中心
- **Then** 所有内容仍可见
- **And** 提醒进入独立提醒
- **And** 不出现伪造的目标归属

### AC6：稳定与响应式

- **Given** 3 秒轮询刷新 `lastCheckedAt`
- **When** 列表成员集合未变化
- **Then** 目标卡片顺序不跳动
- **And** 390px 视口无横向滚动
- **And** 所有颜色状态有对应文本

## 13. 风险与开放问题

| 风险 / 问题 | 影响 | 建议 |
| --- | --- | --- |
| 用户把「目标提醒」理解为“任意时间点提醒我” | 与 `Monitor` 的页面检查语义不符 | 文案明确为“条件提醒 / 检查节奏”；P2 再评估无 URL 的轻量目标提醒 |
| 目标没有 `updatedAt` | 无法准确计算“多少天未推进” | P0 不展示精确停滞天数；需要时先补字段 |
| 目标暂停导致关联提醒任务暂停 | 用户可能误以为提醒仍在工作 | 目标轨道显示「随目标暂停」，并提供恢复入口 |
| 提醒数量多时目标卡片过长 | 降低扫读效率 | 最多展示 2 条，其余折叠为「另有 N 条」 |
| 排序逻辑随需求膨胀 | 难以解释和测试 | 固定优先级表；阈值进配置常量；不引入模型排序 |
| 通知分组依赖任务仍存在 | 任务缺失时无法归属目标 | 回退到「独立」，不隐藏通知 |

待产品确认：

1. 目标轨道是否默认显示已完成目标？（建议折叠，不默认展开。）
2. 独立提醒是否允许一键关联已有目标？（建议 P1 开放，P0 只在新提醒创建时关联。）
3. 「接下来」是否在首页工作台也展示？（建议先只在任务中心验证，避免首页信息过载。）
4. 每日目标摘要是否合并进现有通知，还是放在目标卡片内？（建议先做卡片内摘要，不新增通知类型。）

## 15. 结论

本方案不把产品做成更复杂的任务管理工具，而是利用现有领域结构提供一个更有判断力的阅读层：

- `Goal` 回答“为什么”；
- `AgentTask` 回答“正在做什么”；
- `Monitor` 回答“什么时候再检查”；
- `AgentNotification` 回答“发生了什么”；
- `TrackingView` 回答“现在先做什么”。

因此，新功能的核心不是新增“提醒对象”，而是新增一个**确定性、可测试、可回滚的视图投影层**。这既改善呈现，也最贴合 LingWu 当前的代码结构。
