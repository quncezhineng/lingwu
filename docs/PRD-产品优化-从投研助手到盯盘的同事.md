# PRD：LingWu 产品优化 —— 从「投研助手」到「替你盯着的同事」

> 版本：v1.0 ｜ 日期：2026-11-12 ｜ 状态：待评审
> 输入：外部文章《证券投顾的 Personal Agent 时代》＋ 本项目现有实现（`docs/FEATURES.md`、`ROADMAP.md`、`docs/O2-定时任务与部署手册.md`、`docs/PRD-多Agent记忆系统.md`、`apps/mobile/src/skill-catalog.ts`）
> 关联文档：`docs/PRD-LingWu-个人投研智能体.md`（v1.0，功能面）、`docs/PRD-任务目标提醒.md`、`docs/UI-SPEC-D1-D2-观察列表与市场简报.md`

## 0. 一页结论

| 问题 | 结论 |
| --- | --- |
| 文章真正在讲什么 | 不是「更聪明的 AI」，而是**注意力的委托**：把「盯着」这件事外包出去，把时间还给判断。 |
| 灵悟现在是什么 | **一个很强的通用个人 Agent，加了一层投研皮肤**。执行能力（浏览器/沙箱/耐久任务/审批回执）是超配的，但「盯」和「记得住」是欠配的。 |
| 最大的结构性错位 | 我们的成功指标衡量「事情有没有做完」，而用户真正在意的是「**该响的时候响没响、不该响的时候闭没闭嘴**」。 |
| 一句话方向 | 把产品重心从 **Chat 驱动的「问答」** 移到 **事件驱动的「今天」**：默认界面不是我打字的地方，是它替我看完、筛完、递上来的地方。 |
| 本 PRD 的核心 | 5 个 P0 需求（盯、论点账本、我的模板、交付物中心、溯源与合规门）＋ 1 次 IA 收敛 ＋ 1 套新度量。 |

北极星指标建议改为：**「周有效打扰数」**——用户点开、并产生了后续动作（追问 / 审批 / 加自选 / 改论点）的推送条数。它同时惩罚漏报和骚扰。

## 1. 文章论点拆解（作为需求依据）

### 1.1 Personal Agent 的三个硬指标

| 能力 | 文章原话要点 | 对产品的真实要求 |
| --- | --- | --- |
| **记得住** | 「你的客户、你的模板、你的判断标准，它长期记着」「越用越深」 | 记忆的对象不是「偏好」，是**可被比对的历史**：上次说了什么、这次兑现没有 |
| **替你盯着** | 「自己排期、自己巡检，到点把结果递到你面前」 | 需要**排期 + 巡检 + 递送**三件套，缺一件就退化成「你主动去查」 |
| **会连起来** | 「邮箱、日历、文件、表格，授权后都能接上」 | 连接器要覆盖**用户实际待的地方**，而不是技术上好接的地方 |

### 1.2 一条原则：只撬三种活

> 重复、耗时、结果能复用 —— 三个条件越齐，杠杆回报越高。

这条原则直接给出了**功能取舍标准**：不满足「可复用」的功能，做得再炫也不该进主路径。

### 1.3 五个值钱场景（本文档的需求来源）

| # | 场景 | 本质 | 灵悟覆盖度（当前） |
| --- | --- | --- | --- |
| 1 | 调研纪要：录音 → 结构化 → 归到人/标的 → 盯待核实项 | 输入形态 + 归档 | ❌ 无语音输入，无实体归档 |
| 2 | 客户/标的陪访：面前一页纸，面后一张清单 | 上下文聚合 | 🟡 有标的全景，无「一页纸」成品 |
| 3 | 晨报与内容：用它保下限，用人保观点 | 排期 + 模板 | 🟡 有定时简报，无模板与观点分离 |
| 4 | 组合检视：定好规则，收盘后自动扫，异动才推 | 事件监控 | 🟡 有价格阈值，非事件、非交易日历 |
| 5 | 知识整理：把积累变成库存 | 可检索资产 | 🟡 有 library/notes，缺结构化与自动归档 |

### 1.4 起步法（必须变成 Onboarding）

> 挑一件你每周都做的重复活 → 跑通 → 把改好的版本定成**固定模板**，连同修改标准存进记忆 → 下次直接出成品。

这是文章的**增长逻辑**，也是灵悟目前最缺的**用户成功路径**。现在的首次体验是「配置模型 Key → 发一条消息」，而不是「选一件你每周做的事」。

### 1.5 三条红线（必须变成产品机制，不能只写进免责声明）

1. 对外建议可以起草，**发出前人审**。
2. **客户信息不出边界**，外部平台需脱敏。
3. 输出**默认是草稿**，数字要复核、出处要查实。

## 3. 七个结构性缺口（诊断）

### G1 「记得住」停留在偏好级，没有资产级记忆

现在的记忆是 `AgentMemory { text, category }` 片段，能记住「我偏好价值投资」，记不住「我 3 月判断宁德时代毛利率见底，理由是 X，现在验证到哪一步」。

文章场景一那句「他上次说了什么、这次兑现没有，一比就知道」——**这是产品最锋利的点，我们现在完全没有承载它的数据结构**。

> 影响：用户用三个月，资产不增长。换一个产品，一切归零。

### G2 「盯」的触发源选错了

我们盯的是**网页上的一个数字**，而投研真正要盯的是**事件**：财报发布、公告、评级调整、股东变动、论点被证伪。

价格阈值监控的尴尬是：**误报低但价值也低**（涨 5% 本身不是信息），而高价值事件我们一个都没接。同时简报固定 UTC 整点触发，A 股/港股/美股用户拿到的东西永远错位。

### G3 「到点递到面前」缺最后一公里

有 inbox，没有 push。这一条看似工程量小，**实际是产品形态的分水岭**：

- 有 push → 产品是「同事」，它来找你；
- 只有 inbox → 产品是「后台」，你得记得去翻。

文章整篇的前提（「有动静它叫你」）在我们的形态里不成立。

### G4 模板复利闭环缺失

文章最有杠杆的一步是「把改好的东西固化成模板 + 把修改标准存进记忆」。我们有 184 个**厂商给的** skill，没有**用户长出来的**模板。

这导致一个反直觉的结果：**产品用得越久，越像一个通用聊天工具**，因为用户的口径没有被沉淀成可复用资产。

### G5 产出形态是「对话」，不是「交付物」

投研的成品形态很明确：晨报、研报 PDF、面谈一页纸、纪要、组合检视表、周报。它们的共同点是**要被审、被发、被归档、被再引用**。

现在产出是 inline card + markdown，缺状态机（草稿/已审/已发）、缺版本、缺 diff、缺导出。结果：**用户每次都要重新组装一遍**。

### G6 输入形态单一（只有打字）

ROI 最高的场景（调研纪要）依赖「录音 → 结构化」。没有 ASR，没有批量 PDF/截图入料，等于主动放弃了文章排第一的场景。

### G7 连接器与用户的实际生活脱节

我们的连接器是 Google + 通用网页。而目标用户的信息在：企业微信/飞书、腾讯文档、雪球、东财公告、券商 App 截图。

「会连起来」这条能力，我们技术上有，产品上等于没有。

### 补充缺口（形态层）

- **G8 首页有壳，内容是别人的**：`TodayScreen` 已经在导航第一位，但承载的是邮件/日历/待办。等于把投研产品做成了日程助手——**位置对了，内容错了**，而这是改造成本最低、感知最强的一处。
- **G9 多 Agent 的认知成本**：`agent-space` 允许多 Agent，但用户不知道该建几个。文章描述的体验是「一个人格统一的管家」。建议改为**场景预设角色**，而不是让用户自己搭班子。
- **G10 缺乏打扰纪律**：没有任何「今天最多打扰你几次」的机制。事件监控一上线，误报会立刻摧毁信任。
- **G11 合规门是文案，不是机制**：有 action review（Gmail/Calendar 写入需审），但没有「数字级出处」和「对外发送合规门」。

## 4. 产品形态判断（三个必须先定的事）

### 4.1 形态一：桌面工作台 + 手机遥控器

| 端 | 角色 | 该做什么 | 不该做什么 |
| --- | --- | --- | --- |
| 桌面 Web（≥1024px 三栏） | **生产端** | 研报、表格、PDF、多标的对比、模板编辑 | 不做信息流 |
| 手机 | **接收端 + 审批端** | 看「今天」、一句话追问、30 秒审批、快速记一条论点 | 不做长文档编辑、不做复杂表单 |

> 理由：文章五个场景里，四个半发生在桌面。手机的价值是「它叫你的时候你在」。现在两端功能对齐，反而两边都不称手。

### 4.2 形态二：「今天」装投研的内容，而不是装日程

导航层其实已经对了——底部第一个 tab 就是 `today`（`shell.tsx:61`），但 `TodayScreen` 装的是未读邮件、日历日程、待办统计，hero 是「给今天腾点空间」。**这是把投研产品做成了日程助手。**

不需要新增首页，需要**换首页的内容模型**：三段式，把投研动线做成主动线，通用能力降为底座：

```
[今天]     ① 今晨简报（3–5 条，可展开）
           ② 待我审批（草稿/论点状态变更，一条一行）
           ③ 今日盯到的异动（按必须知道/可以稍后分组，一句话一条）
           ④ 我的活跃论点回检结果（本周到期几条）
[对话]     问答与追问（保留现有 chat，降为二级）
[盯]       规则中心：按 标的 / 事件 / 论点 三组，含打扰预算
[产出]     交付物中心 + 我的模板
[我的]     组合 / 观察列表 / 知识库 / 记忆 / 口径 / 连接器
```

关键变化：**「今天」是一个由任务生成、可被审批的页面，而不是一个空输入框**。邮件/日历卡片不必删，降级到「我的 → 连接器」即可（`HIDDEN_TODAY_SECTIONS` 已有现成开关，改一行即可下线）。

### 4.3 形态三：一个管家，多个「姿势」

不做「多 Agent 让用户自己搭」，做 **Role Preset**：投研助手 / 纪要整理 / 复盘教练 / 组合检视。切换的是**口径与默认动作**，不是人格。底层复用现有 agent-space，但不暴露「建 Agent」这个动作。

## 6. P0 详细需求

### OPT-01 「盯」升级

**现状问题**

- 监控只支持公开网页文本/价格阈值（`FEATURES.md` 明确标注非交易日历、非实时）。
- 简报按固定 UTC 整点触发，不认用户时区与交易日（`O2` 手册 §1.2）。
- 通知仅应用内 inbox，无 push。

**用户故事**

> 作为盯 5 只票和一个组合的投资者，我希望它只在**真正该知道的时候**叫我一次，而不是让我每天翻三个 App。

**功能行为**

1. **事件源四层分级**

   | 层 | 事件 | 触发方式 | 默认打扰级别 |
   | --- | --- | --- | --- |
   | L1 | 行情异动：阈值 / 相对成交量 / 波动率突增 | 轮询行情 API（1–5 min） | 归档（进「今天」不弹） |
   | L2 | 财报发布、公告、分红除权、停复牌 | 公告源 + 财报日历 | 必须知道 |
   | L3 | 新闻/研报评级变动、目标价调整 | 搜索 + 指定源 | 可以稍后 |
   | L4 | 论点相关信号（触发某条论点的证伪条件） | 由 OPT-02 注册 | 必须知道 |

2. **交易日历**：A 股/港股/美股各自日历，按**标的所属市场**判断；非交易日不跑 L1/L2，只出「周末回顾」。
3. **打扰预算（Attention Budget）**：每人每日默认上限 5 条「必须知道」；超额自动降级为 19:00 汇总；用户可调 1–10。
4. **投递通道**：APNs/FCM（移动）、邮件、Webhook、企业微信机器人。同一条事件多渠道只投一次，记录 `delivery_log`。
5. **静默期**：用户本地时间 22:00–07:00 默认静默（L2 可穿透）。
6. **去重与冷却**：同标的同类事件 4 小时内合并；同一规则连续 3 次被用户标「不必要」→ 自动降频并提示。

**验收标准**

- 误报率（用户标记「不必要」）≤ 10%；有效打扰率（被点开且产生后续动作）≥ 60%
- 推送 P95 延迟：L1 ≤ 2 min，L2 ≤ 30 min（受数据源限制需在 UI 标注）
- 单用户日推送 ≤ 预算 +1（汇总算 1）
- 非交易日零 L1/L2 推送
- 关闭某规则后 1 个 tick 内生效

**涉及模块**

`apps/server/src/engine/briefing-scheduler.ts`（扩展为通用调度）、新增 `monitor-engine.ts`、`delivery/`（APNs/FCM/Webhook）、`apps/mobile/src/tracking-screen.tsx`、`notification-actions.ts`、`price-alerts.ts`

**数据模型增量**

```ts
MonitorRule {
  id, ownerId, targetType: 'symbol'|'portfolio'|'thesis'|'page'
  targetId, eventKinds: EventKind[]
  market?: 'CN'|'HK'|'US'          // 决定交易日历
  level: 'MUST_KNOW'|'LATER'|'ARCHIVE'
  cooldownMinutes, enabled, quietHours?
}
MonitorEvent {
  id, ruleId, kind, severity, payload, dedupeKey
  detectedAt, marketDate, state: 'new'|'delivered'|'archived'|'dismissed'
}
DeliveryLog { id, eventId, channel, sentAt, providerId, result }
AttentionBudget { ownerId, date, limit, used, downgradedCount }
```

### OPT-02 论点账本（Thesis Ledger）

**现状问题**

- `InvestmentNote` 只是「笔记 + 可空 thesis_status」，没有主张/证伪条件/证据绑定。
- 记忆是偏好片段，无法回答「上次的判断兑现了吗」。

**用户故事**

> 作为有自己判断的投资者，我希望我的每个判断都被记下来、被跟踪、到期被追问一句「它还成立吗」——这样三个月后我知道自己到底准不准。

**功能行为**

1. **论点卡**：`主张（一句话）/ 标的 / 假设 / 证伪条件（可调用 OPT-01 注册监控）/ 期限 / 置信度 / 关联证据[]`
2. **证据绑定**：每条论点至少 1 条证据，含 `url / 发布日期 / 引用数字 / 抓取时间`。证据失效（链接 404 或数据变更）标灰并提示。
3. **自动回检**：每周 + 财报发布后 24h，Agent 用最新信息回检，输出「仍成立 / 待验证 / 已被证伪」＋理由＋证据。
4. **状态变更必须人审**：Agent 只能提交建议，用户确认后状态才变（沿用现有 action review 机制）。
5. **言行比对**：同一标的 / 同一信息源（如某基金经理）的历史观点时间线，可一键看「上次说了什么 → 后来怎样」。
6. **判断胜率**（轻量版）：已了结论点的命中率，仅统计有证伪条件且到期结案的论点。

**验收标准**

- 创建论点 ≤ 3 步，可纯语音/一句话生成草稿后确认
- 每条论点 100% 有至少 1 条可点开证据，否则不允许设为「活跃」
- 回检任务成功率 ≥ 95%，漏检（应检未检）≤ 1%
- 状态变更 100% 走人审，审计日志可查

**涉及模块**

`note-ui.tsx` / `notes-screen.tsx` / `notes.ts`（扩展）、新增 `thesis.ts`、`apps/server/src/engine/thesis*.ts`、与 `finance` / `research.ts` 打通

**数据模型增量**

```ts
Thesis {
  id, ownerId, symbolId, claim, assumption
  falsifyCondition: { kind, expression }   // 可映射为 MonitorRule
  horizon: { from, to }, confidence: 0..1
  status: 'ACTIVE'|'PENDING'|'INVALIDATED'|'EXPIRED'
  evidence: EvidenceRef[], createdAt, closedAt?
}
ThesisReview {
  id, thesisId, reviewedAt, verdict, rationale
  proposedStatus, approvedBy?: 'user', evidence: EvidenceRef[]
}
EvidenceRef { url, publishedAt, quoteNumber?, fetchedAt, healthy: boolean }
```

### OPT-03 我的模板（口径沉淀）

**现状问题**

- 184 条技能是只读内置（`skill-catalog.ts`），无用户自建、无「从一次产出反推模板」的路径。
- 用户的修改标准无处存放，每次重新交代。

**用户故事**

> 我改了三遍晨报，第四遍不想再改。我希望它能学会我改了什么，然后每次都按我的口径来。

**功能行为**

1. **入口**：任一交付物/回答 → 「存为模板」，≤ 3 步。
2. **自动抽取**：结构（章节顺序）、字段（必填项）、口径（语气/单位/口径说明）、**反例**（本次我删掉/改掉的句子）。
3. **命中机制**：新任务自动匹配模板，**展示命中理由**并允许换模板；命中不准可「不是这个」以修正。
4. **模板质量分**：复用后人工改动字符数 / 总字符数。改动率持续 > 30% 提示「口径可能不清晰」。
5. **两张表分离**：`内置能力`（184 条，只读）vs `我的口径`（用户模板，可编辑、可分享给同团队）。
6. **版本**：模板带版本号，历史交付物记录所用模板版本。

**验收标准**

- 从一次产出到模板可用 ≤ 3 步、≤ 30 秒
- 模板复用后人工改动下降 ≥ 40%（对比首次）
- 模板命中准确率 ≥ 80%（用户「不是这个」比例 ≤ 20%）
- 内置技能与用户模板在 UI 上清晰分离，不混排

**涉及模块**

新增 `templates.ts`、`template-editor.tsx`、`apps/server/src/engine/templates.ts`；复用 `skill-editor.tsx` 的编辑壳

### OPT-04 交付物中心（Deliverables）

**现状问题**

- 产出散在 chat 卡片 / artifact / notes / PDF，无统一对象、无状态、无版本。

**用户故事**

> 我要的是「能发给别人的东西」，不是一段聊天记录。

**功能行为**

1. **一等公民**：`Deliverable` 类型 = 晨报 / 研报 / 纪要 / 一页纸 / 复盘 / 表格 / 自定义。
2. **状态机**：`draft → in_review → approved → sent / archived`。**默认 draft**。
3. **版本与 diff**：每次修改生成版本，可看「Agent 改了什么 / 我改了什么」。
4. **导出**：PDF、DOCX、Markdown、飞书/腾讯文档（P1）、分享链接（带免责声明与只读权限）。
5. **手机审批**：手机上 30 秒内完成「看关键改动 → 批准 → 发送」。
6. **回链**：交付物引用其来源（简报任务 / 标的 / 论点 / 纪要），可反向追溯。

**验收标准**

- 所有定时任务产出自动落到交付物中心（不再只存在 chat 里）
- 手机端审批路径 ≤ 3 次点击
- 导出 PDF 排版错位率 = 0（抽样 20 份人工检查）
- 每个交付物可追溯到生成它的任务与所用模板版本

**涉及模块**

`briefing-card.tsx` / `report-brief-card.tsx` / `note-ui.tsx` 收敛、新增 `deliverables.ts` + `deliverable-view.tsx`、`apps/server` 新增 `/deliverables` 路由

### OPT-05 溯源与合规门

**现状问题**

- 搜索有 evidence，但数字/结论不强制带出处（`FEATURES.md` 仅说明「sources include URLs and excerpts」）。
- 有 action review，但无「对外发送合规门」、无免责声明注入、无客户信息脱敏。

**用户故事**

> 我要能一键确认「这句话不是它编的」，且在发出去之前有人替我把合规关。

**功能行为**

1. **数字级引用**：交付物中任一数字可点开 → 来源 URL + 抓取时间 + 原文片段。
2. **无源拦截**：无法溯源的数字自动标黄，要求「补来源 / 删掉 / 标为估算」三选一，未处理不允许 approved。
3. **合规门**（approved → sent 之间强制）：
   - 免责声明自动注入（可配置文案）
   - 违禁表述检测（收益承诺、保本、「稳赚」等词库 + 模型复核）
   - 客户信息脱敏（姓名/账号/持仓数字，规则 + 模型双检）
4. **草稿态默认**：所有对外内容默认 draft；`sent` 只能由人触发。
5. **审计日志**：谁、何时、改了哪句、谁批准、发给了谁，全量留痕（复用 `lingwu_audit_logs`）。

**验收标准**

- 对外交付物 100% 含免责声明
- 无源数字拦截率 100%（不允许带病 approved）
- 合规门 P95 ≤ 3 s
- 审计日志可导出，覆盖率 100%

## 8. 度量体系（替换现有成功标准）

### 北极星

**周有效打扰数（Weekly Effective Nudges, WEN）** = 用户点开且产生后续动作（追问/审批/加自选/改论点）的推送条数 / 周活用户。

### 核心指标

| 指标 | 目标 | 反面指标（必须同时看） |
| --- | --- | --- |
| 有效打扰率 | ≥ 60% | 用户标记「不必要」比例 ≤ 10% |
| 论点存活率（30 天仍有回检） | ≥ 50% | — |
| 模板复用率（有模板用户的交付物中命中模板占比） | ≥ 40% | 模板平均改动率 ≤ 30% |
| 交付物 approved→sent 转化 | ≥ 35% | 合规门拦截率（过高说明质量差） |
| D7 留存 | ≥ 30% | 推送关闭率 ≤ 15% |
| 周活跃天数 | ≥ 4 天 | — |

> 注：`docs/PRD-LingWu-个人投研智能体.md` §3.2 的旧指标（简报生成成功率、研究完成时间）保留为**健康度指标**，不再是产品成败指标——它们只证明「机器没坏」。
