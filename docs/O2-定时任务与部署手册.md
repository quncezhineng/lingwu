**版本**: 1.1（P1 增补：财报 PDF 解析依赖与健康自检）｜**日期**: 2026-10-27｜**负责人**: DevOps

## 0. 结论摘要

1. **每日简报定时触发已补齐（代码）**：新增 `apps/server/src/engine/briefing-scheduler.ts`，由 **task worker 的维护周期（60s）** 驱动；每个有观察列表的 owner 每 UTC 日期创建一个持久 `market_briefing` 任务，任务由现有耐久引擎执行。
   - 幂等：同一 owner/date/attempt 使用固定 idempotencyKey，不会重复建任务；
   - 补跑：进程宕机后首次 tick 自动补当天未生成的简报；
   - 重试：失败后间隔 5 分钟再试，**每天最多 3 次**；成功后当天不再创建。
2. **必须显式开启**：`BRIEFING_SCHEDULE_ENABLED=true`（默认关闭，避免测试/演示环境自动产任务）。未设置时仍只有手动 `POST /api/briefings/generate`。
3. **akshare 自检已接入**：
   - `GET /api/health` 新增 `market_data.akshare`：`available | unavailable | disabled | checking`，附 `version` 或 `reason`；
   - API 与 worker 启动时各跑一次探测，结构化日志 `phase=akshare-self-check`；
   - 本机实测（python3 存在、akshare 未安装）→ `unavailable / akshare_missing`，可据此在部署验收时发现 A 股链路缺失。
4. **财报 PDF 解析自检已接入（P1）**：
   - `GET /api/health` 新增 `pdf: { status, version?, reason?, detail?, checked_at? }`，`status` 为 `available | unavailable`；
   - `reason`：`binary_missing | timeout | error`；未完成首次探测时返回 `unavailable + reason=error + detail="probe pending"`，随后自动刷新；
   - API 与 worker 启动时各跑一次 `pdftotext -v` 探测（本 PR 补齐启动自检），日志 `phase=pdf-self-check`；
   - 缺失时 PDF 上传返回 422（可粘贴文本），不影响行情/简报/组合等功能。
5. **生产 worker 运行方式**：PostgreSQL 场景推荐「API + 独立 worker」；worker 必须带 `DATABASE_URL`，启动命令 `pnpm start:worker`。

## 1. 定时触发设计

### 1.1 链路

```
AgentService.start()
  └─ setInterval(maintain, 60s)
       └─ maintain()
            └─ briefingScheduler.runOnce()          // 仅在运行 worker 的进程
                 ├─ db.scan("watchlists") → 有观察列表的 owner
                 ├─ 当天无 queued/running/scheduled/paused/succeeded 任务？
                 ├─ 失败次数 < 3 且距上次尝试 ≥ 5 分钟？
                 └─ createTask(kind=market_briefing,
                               idempotencyKey="market-briefing:{owner}:{date}:{attempt}")
TaskWorker.tick() (1s 轮询, 并发 3, 租约 + 心跳)
  └─ execute() → generateMarketBriefing()（按日幂等, 支持部分数据 + data_status）
       ├─ records: market_briefings（简报正文/指数/标的动态/events 状态）
       └─ agent-artifacts: kind=market_briefing
```

### 1.2 触发时间

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `BRIEFING_SCHEDULE_ENABLED` | 关闭 | 生产必须设为 `true` |
| `BRIEFING_SCHEDULE_UTC_HOUR` | `0` | UTC 整点小时（0-23）。UTC 00:00 = 北京 08:00，A 股盘前；美股收盘后约 20:00 ET |

> 时区固定 UTC，不支持按用户时区单独调度（P1）。`maintain` 每 60s 检查一次，实际生成时间在配置整点后 1 分钟内开始。

### 1.3 幂等 / 补跑 / 重试

| 场景 | 行为 |
| --- | --- |
| 同一 owner 当天已有 queued/running/scheduled/paused/succeeded 任务 | 跳过，不重复创建 |
| worker 进程在 00:00 宕机、10:00 重启 | 首次 maintain 即补建当天任务（无 24h 上限，当天内补跑） |
| 任务执行失败（行情超时/内部错误） | `task.status=failed` + `task.error`；调度器 5 分钟后建下一次尝试，最多 3 次/天 |
| 达到 3 次仍失败 | 当天不再创建；日志 `phase=briefing-schedule outcome=skipped reason=attempts_exhausted` |
| 用户手动 `POST /api/briefings/generate` | 直接生成，不产生任务；与定时任务共用按日幂等逻辑，不会重复写入 |
| 无观察列表的用户 | 不自动创建（P0 决定：简报内容围绕观察列表；此类用户仍可手动生成） |

### 1.4 多进程约束

- 调度只在 **运行 worker 的进程** 生效（`agent.start()` 调用方）：
  - 单进程部署：API 进程 `TASK_WORKER_ENABLED=true`（默认）；
  - 拆分部署：API 设 `TASK_WORKER_ENABLED=false`，独立 worker 进程 `pnpm start:worker`。
- 即使误起两个 worker，`createTask` 的固定 id + `insertIfAbsent` 保证同一 owner/date/attempt 只有一条任务记录。

## 2. 部署与启动

### 2.1 单进程（PGlite，适合 demo/单机）

```bash
cp .env.example .env          # 填 CPK_INTELLIGENCE_API_KEY、TOKEN_ENCRYPTION_KEY 等
pnpm install
pnpm typecheck && pnpm test   # 发布前验证
pnpm build:server && pnpm start
# 开发模式：pnpm dev
```

### 2.2 生产（PostgreSQL + 独立 worker，推荐）

```bash
# 共享配置（两个进程一致）：DATABASE_URL / DATA_DIR / TOKEN_ENCRYPTION_KEY /
# CPK_INTELLIGENCE_API_KEY / BRIEFING_SCHEDULE_ENABLED=true ...

# API 进程（不跑 worker）
TASK_WORKER_ENABLED=false pnpm start

# Worker 进程（跑 durable 任务与每日调度；worker-entry 强制要求 DATABASE_URL）
pnpm start:worker
```

- `pnpm start` / `pnpm start:worker` 使用 `dist/`，需先 `pnpm build:server`；
- worker 与 API 需同版本部署，共享同一个 `DATABASE_URL`；
- PDF 等文件落盘在 `DATA_DIR`，拆分部署时两个进程需共享（NFS/PVC 或同一主机卷）。

### 2.3 部署验收（必做）

```bash
# 1) 进程健康
curl -s http://127.0.0.1:8787/api/health | jq
# 期望: .ok == true

# 2) A 股链路（F-02）
curl -s http://127.0.0.1:8787/api/health | jq '.market_data.akshare'
# available → A 股走 AKShare（实时）；unavailable → 仅 Yahoo（约 15 分钟延迟）；
# disabled → 显式关闭；checking → 首次探测中，5 秒后重试

# 3) 财报 PDF 解析链路（P1）
curl -s http://127.0.0.1:8787/api/health | jq '.pdf'
# available → PDF 上传可解析；unavailable → /api/financials/parse 的 PDF 请求返回 422
# （文本粘贴解析仍可用）。刚启动的极短窗口可能返回 detail="probe pending"，1-5 秒后复查。

# 4) 定时调度（启用后）
#    观察 API/worker stdout: 每天配置整点出现
#    {"context":{"phase":"briefing-schedule"},"outcome":"enqueued","date":"YYYY-MM-DD","attempt":1}
```

### 2.4 AKShare 安装与失败表现（F-02）

| 项 | 内容 |
| --- | --- |
| 依赖 | `python3`（建议 3.11+）与 `akshare` Python 包 |
| 安装 | `python3 -m venv /opt/lingwu/py && /opt/lingwu/py/bin/pip install akshare==<锁定版本>` |
| 指定解释器 | `AKSHARE_PYTHON=/opt/lingwu/py/bin/python`（默认 `python3`） |
| 验证 | `${AKSHARE_PYTHON:-python3} -c "import akshare; print(akshare.__version__)"` |
| 单次取价超时 | `MARKET_DATA_AKSHARE_TIMEOUT_MS`（默认 5000ms） |
| 关闭回落 | `MARKET_DATA_AKSHARE_ENABLED=false` |
| 缺失表现 | A 股请求回落 Yahoo（约 15 分钟延迟）；`/api/health` → `unavailable` + `reason`；日志 `phase=akshare-self-check` |
| 分类 | `python_missing`（未安装 python3）、`akshare_missing`（模块缺失）、`timeout`（探测超时）、`error`（其他） |

> 本仓库开发机实测：`python3` 存在但未安装 akshare → `{"status":"unavailable","reason":"akshare_missing"}`，符合预期；**A 股用户部署前必须安装**，否则 P0「A 股实时行情」退化为 15 分钟延迟。

### 2.6 生产推荐取值与影响范围（发布前一次性核对）

| 变量 | 推荐生产值 | 直接影响（用户可感知） | 调整副作用 / 注意 |
| --- | --- | --- | --- |
| `BRIEFING_SCHEDULE_ENABLED` | **`true`** | 决定「每日简报是否自动出现」：`false` 时用户只能手动「立即生成」 | 默认关闭；开启后每个有观察列表的 owner 每天 1 个任务（最多 3 次尝试） |
| `BRIEFING_SCHEDULE_UTC_HOUR` | `0` | 简报生成时间：UTC 00:00 = 北京 08:00（A 股盘前）、美股收盘后约 20:00 ET | 调大 → 当天简报更晚；不影响已生成简报 |
| `MARKET_DATA_QUOTE_TIMEOUT_MS` | `5000` | 单标的取价上限：超时后该标的显示 `error=timeout` 并进 `unavailable`，不拖累整页 | 调大 → 慢数据源更容易返回，但观察列表/简报整体变慢；调小 → 更易出现部分数据缺失 |
| `MARKET_DATA_SUMMARY_TIMEOUT_MS` | `10000` | 观察列表 summary 的整体预算：到点先返回已完成部分 | 与 F-01 验收阈值绑定（≤10s），不建议调大 |
| `MARKET_DATA_SEARCH_TIMEOUT_MS` | `5000` | 标的搜索响应时间上限 | 超时后搜索报错/空结果；调大只会让用户多等 |
| `MARKET_DATA_BRIEFING_TIMEOUT_MS` | `20000` | `POST /api/briefings/generate` 总预算（行情 10s + 生成） | 与 F-01 验收阈值绑定（≤20s）；调小更易产出 partial 简报 |
| `MARKET_DATA_BRIEFING_MARKET_TIMEOUT_MS` | `10000` | 简报内行情阶段预算：到点用降级要点并标注部分数据不可用 | 调大 → 简报更完整但更慢；调小 → 部分数据缺失增多 |
| `MARKET_DATA_AKSHARE_TIMEOUT_MS` | `5000` | A 股 AKShare 单次取价上限：超时即回落 Yahoo（约 15 分钟延迟） | 调大 → A 股偶发慢请求更易成功，但会让 summary 更早触碰整体预算 |
| `MARKET_DATA_AKSHARE_ENABLED` | `true`（A 股用户必须） | A 股实时数据链路：`false` 时 A 股仅有 Yahoo 15 分钟延迟 | 关闭只影响 A 股，不影响美股；`/api/health` 会显示 `disabled` |
| `AKSHARE_PYTHON` | venv 绝对路径（如 `/opt/lingwu/py/bin/python`） | 决定 A 股链路是否可用 | 配错 → `akshare_missing`/`python_missing`，A 股静默降级 |
| `MARKET_DATA_HEALTH_TTL_MS` | `300000` | `/api/health` 中 akshare 状态的新鲜度 | 调小 → 探测更频繁（每次都会起 python 子进程） |
| `TASK_WORKER_ENABLED` | 单进程 `true`；拆分部署 API 侧 **`false`**，worker 侧必须运行 | 决定持久任务是否被执行：监控、价格提醒、**每日简报调度**全部依赖 worker | API 与独立 worker 同时开 worker 不会重复执行（租约 + 固定 key），但会浪费资源；**没有 worker = 没有定时简报** |
| `DATABASE_URL` | PostgreSQL 连接串（拆分部署必填） | 多进程共享任务/简报数据 | 缺失时 `pnpm start:worker` 直接拒绝启动 |
| `MARKET_DATA_CACHE_TTL_MS` | `60000` | 行情新鲜度（P0 要求 ≤1 分钟刷新） | 调大 → 行情更旧；调小 → 上游调用量上升，可能触发限流 |
| `MARKET_DATA_STALE_CACHE_TTL_MS` | `300000` | 降级窗口：上游不可用时最多返回 5 分钟旧数据 | 调大 → 更耐故障但数据更旧；超过窗口返回错误 |
| `MARKET_DATA_CACHE_MAX_SIZE` / `MARKET_DATA_RATE_LIMIT_PER_MINUTE` | `10000` / `60` | 缓存容量与单用户查询频率上限 | 多用户规模化时按内存与上游配额调整 |
| `PDFTOTEXT_BIN` | `pdftotext`（或 poppler 绝对路径） | 决定财报 **PDF 上传能否解析**：缺失时 `POST /api/financials/parse` 的 PDF 请求返回 422，文本粘贴仍可用 | 配错/未安装 → `/api/health` `pdf.status=unavailable`；不影响行情、简报等其它功能 |
| `PDF_HEALTH_TTL_MS` | `300000` | `/api/health` 中 pdf 状态的新鲜度 | 调小 → 探测更频繁（每次起一个 pdftotext 子进程，开销很小） |
| `PDF_HEALTH_TIMEOUT_MS` | `3000` | pdf 自检的探测超时 | 容器冷启动磁盘慢时可调大；调大只会让首次探测更慢返回 |

**发布核对顺序**：先确认 `TASK_WORKER_ENABLED` 与 worker 进程 → `BRIEFING_SCHEDULE_ENABLED=true` → `AKSHARE_PYTHON` + `MARKET_DATA_AKSHARE_ENABLED=true` → 安装 poppler 并确认 `pdf.status=available` → `curl /api/health` 中 `market_data.akshare.status=available` → 次日观察 `phase=briefing-schedule outcome=enqueued`。任一不满足都写入发布记录。

### 2.7 财报 PDF 解析依赖（pdftotext / poppler，P1）

| 项 | 内容 |
| --- | --- |
| 依赖 | poppler 的 `pdftotext` 命令行工具（调用方式为 stdin→stdout：`pdftotext - -`） |
| 版本 | poppler ≥ 22.02（22.02 / 24.02 的 `-v` 版本输出已兼容）；使用发行版自带包，容器内锁定镜像版本 |
| 安装（Debian/Ubuntu） | `apt-get update && apt-get install -y poppler-utils` |
| 安装（macOS） | `brew install poppler` |
| 安装（Alpine） | `apk add --no-cache poppler-utils` |
| 安装（RHEL/CentOS） | `dnf install -y poppler-utils` |
| 指定二进制 | `PDFTOTEXT_BIN=/usr/bin/pdftotext`（默认使用 PATH 中的 `pdftotext`） |
| 验证 | `pdftotext -v`（输出类似 `pdftotext version 24.02.0`） |
| 健康检查 | `curl -s http://127.0.0.1:8787/api/health \| jq '.pdf.status'` → `available`；完整对象见 `/api/health` 的 `pdf` 字段 |
| 缓存/超时 | `PDF_HEALTH_TTL_MS`（默认 5 分钟）、`PDF_HEALTH_TIMEOUT_MS`（默认 3 秒） |
| 启动日志 | `{"context":{"phase":"pdf-self-check"},"pdf":{"status":"available","version":"24.02.0"}}` |
| 缺失表现 | PDF 上传 → HTTP 422 `PDF text extraction is unavailable (install pdftotext or send extracted text)`；`text` 粘贴解析、行情、简报、组合、笔记均不受影响 |
| 分类 | `binary_missing`（未安装或路径错误）、`timeout`（探测超时）、`error`（其它） |
| 部署要求 | **API 进程必须安装**（财报解析在 API 内执行）；worker 进程同样会做启动自检并输出日志 |

> 首次探测完成前，`/api/health` 的 `pdf` 会返回 `unavailable + reason=error + detail="probe pending"`，后台探测完成后自动更新为真实结果；发布脚本/自动化检查请重试 1-2 次（间隔 2-5 秒）。本仓库开发机实测（未安装 poppler）→ `unavailable / binary_missing`，符合预期。
>
> 若手动 `pdftotext -v` 可用但自检仍为 `unavailable`，请检查该发行版 `-v` 的退出码与版本输出格式，并把输出反馈给后端调整探测兼容性。

## 3. 失败重试与告警落点

### 3.1 落点一览

| 层级 | 落点 | 内容 |
| --- | --- | --- |
| 任务 | `records(tasks)` | `status=failed`、`error`、`attempts`、`updatedAt` |
| 任务事件 | `records(run-events)` | `kind=error`、`"Task needs attention"`、失败详情 |
| 任务运行 | `records(runs)` | `status=failed|interrupted`、起止时间 |
| 调度 | stdout JSON | `phase=briefing-schedule`、`outcome=enqueued|failed|skipped`、`date`、`attempt` |
| 环境自检 | stdout JSON | `phase=akshare-self-check`、`market_data.akshare.{status,version,reason}` |
| 环境自检（PDF） | stdout JSON | `phase=pdf-self-check`、`pdf.{status,version,reason}` |
| 行情调用 | stdout JSON | `market-data.ts` 结构化日志：provider/symbol/错误分类/timeout |
| 系统异常 | stdout JSON | `log.ts backgroundFailure`：`phase=task worker tick|briefing schedule` |

> 日志统一为单行 JSON，容器采集 stdout/stderr 即可；任务与事件记录在数据库，便于按 owner 追溯。

### 3.2 建议告警规则（P0 手工值班版）

1. `phase=akshare-self-check` 且 `market_data.akshare.status=unavailable` → 部署验收失败/A 股降级（告警级别：warning；持续 10 分钟升级）。
2. `phase=pdf-self-check` 且 `pdf.status=unavailable` → 财报 PDF 上传不可用（warning；P0 不阻断，发布记录注明；P1 若含 PDF 解析则为 critical）。
3. `phase=briefing-schedule`、`outcome=skipped`、`reason=attempts_exhausted` → 当日简报生成失败（warning）。
4. `phase=briefing-schedule`、`outcome=failed` 连续 2 次 → worker 无法建任务（critical）。
5. `tasks` 表中 `kind=market_briefing AND status=failed` 数量 > 0 且持续 15 分钟 → 简报失败（warning）。
6. `/api/health` 连续 3 次 5xx / 超时 → API 不可用（critical，交给运维告警系统）。

> 当前仓库没有内置告警通道（无 Prometheus/PagerDuty 接入）；P0 采用「日志字段 + 人工/外部告警」方式，P1 再接入指标与告警平台。

## 5. 残余风险与边界

1. **未开启开关 = 无定时**：`BRIEFING_SCHEDULE_ENABLED` 默认关闭，部署清单遗漏会退回手动生成。
2. **UTC 固定时区**：不按用户时区调度；全球用户的最佳时间需要 P1 支持。
3. **无独立告警通道**：目前落日志 + 数据库记录，需外部监控采集。
4. **调度规模**：每 tick 最多处理 200 个 owner，超出部分下个 tick 继续；大规模多租户需要分片（P1）。
5. **AKShare 稳定性**：非官方接口，可能随上游变化失效；已有超时（5s）+ 缓存 + Yahoo 兜底，健康检查可及时发现。
6. **定时任务与手动生成并存**：同一天定时任务会复用已存在简报（按日幂等）；`force` 手动重建仍可用，但不会清除已有任务记录。
7. **财报 PDF 解析依赖外部二进制**：容器镜像未装 poppler 时 PDF 上传 422（文本粘贴可用）；`/api/health` 的 `pdf.status` 可在发布前发现，需把安装步骤固化进镜像/主机初始化。
