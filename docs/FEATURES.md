# LingWu feature inventory

The native and web agent core runs locally. This inventory describes the current implementation and remaining extensions. Live providers and optional infrastructure require separate configuration and validation.

The Linux computer is disabled until configured on the server and has no network access. It is a single-owner container with a persistent `/workspace`, separate from the browser worker; see [computer setup and limits](COMPUTER.md). It is not a graphical desktop or a full OS VM.

With the `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` trio set, the server runs email accounts instead of the shared `LINGWU_ACCESS_KEY`. Sign-up, sign-in and verification-code sign-in are proxied through Supabase; the server then issues its own standard JWT session (configurable TTL via `SESSION_TTL_MS`, default 7 days), so later requests do not call Supabase again. Sessions are tracked server-side so a user can list and remotely revoke their other devices, and sign-in is rate-limited by both client IP and account to blunt brute force. Supabase also stores the audit log (`lingwu_audit_logs`) and a resource index (`lingwu_resources`) with row-level security, while business data stays in the LingWu database, namespaced by account id so threads, ideas, goals, notifications and file metadata are private to one account.

Sandbox isolation is per account: the browser worker creates an isolated Chromium profile per session, and the optional Linux computer runs in its own container or E2B Desktop sandbox per owner, so accounts on the same server do not share browser state or computer containers.

Model chat can read the connected primary calendar for an explicit time range of up to 366 days. Missing dates or time zones need clarification. A reply uses at most 20 events and bounded event text; partial results and connection failures are reported. All-day dates keep their calendar time zone and exclusive end date. Calendar changes still require action review. The sample agent's canned replies do not provide this model tool.

Chat and delegated tasks resolve the user's model connection first and fall back to the deployment `MODEL`, written as `provider/model-id`. Deployment providers include OpenAI, Anthropic, Google, DeepSeek and Moonshot. DeepSeek and Moonshot have separate server-only keys (`DEEPSEEK_API_KEY`, `MOONSHOT_API_KEY`) and endpoints. Provider keys stay on the server and never reach the app or the computer sandbox.

My → Settings contains Model connection with linked provider/model dropdowns and a write-only API Key (DeepSeek first). The Bot management sheet has a configured-model selector below Goals and memory, displaying the current model label (for example DeepSeek-Flash). Model selection is kept out of the message composers. Provider endpoints and model parameters come from a shared server catalogue; users cannot override them. The key is encrypted with `TOKEN_ENCRYPTION_KEY` and stored under the authenticated owner and provider, together with a model ID reference. Testing reads the provider's model directory without saving or generating content; saving validates that directory before enabling the connection. Chat turns and delegated model tasks resolve the owner's credentials at execution time. Personal settings override deployment defaults, and removing them restores the deployment default. Redirects are refused.

Bot management's Tasks entry and the chat's active-task banner open the same task-center modal, backed by the authenticated account's task workspace. The management card counts all tasks; the chat banner counts ongoing tasks. Both open the Tasks tab with the existing status filters, execution details and controls; scheduled reminders remain available in the same task center. Closing the modal returns directly to the main screen. There is no separate Bot-only schedule page. The library, skills, analysis history, goals and memory have separate modal components under `apps/mobile/src/bot-pages`. Bot identity editing opens a separate form and saves only when submitted. Library results and analysis history are scoped to the current Bot's thread; goals and memory remain shared by the authenticated account.

Task cards show the title, a concise status and update time; they do not preview execution errors, questions or result dumps. Tasks needing input show a blue attention hint. The detail modal keeps progress, controls, safe results and input/review forms, while hiding execution prompts, raw source excerpts, diagnostic errors, timelines and JSON editing. Failed tasks use a neutral “Not completed” label, preserving their actual state and retry action. Internal diagnostics remain in the stored execution records.

Healthy queued, running or scheduled monitoring tasks with a rule reference display “Monitoring” in both the task list and detail modal. Scheduled tasks awaiting another attempt after an error display “Waiting to retry”; pauses, terminal states and incomplete setup never imply healthy monitoring.

Reminders require a real monitoring rule linked to their execution task. Direct delegation cannot create an orphan monitor task. Resume/retry validates the authenticated owner's rule and task link; incomplete legacy records return `TASK_SETUP_REQUIRED` without queueing work. The task detail shows a setup-required explanation and disables recovery actions for those incomplete records, rather than asking users to retry a permanent configuration issue.

Chat tool cards translate unsuccessful or missing creation receipts into a concise explanation without rendering validation errors. They show a resource link only after receiving a saved receipt; an existing task still opens its real record. Model guidance explicitly separates delegated jobs from monitoring rules. Original tool diagnostics remain in the saved transcript.

Webpage price watches support CNY (including RMB), HKD and USD. The monitoring rule stores a canonical currency, with a selector in its edit form and currency labels in reminder summaries. Common currency codes, symbols and Chinese names are recognized before or after the price, including full-width digits, thousands separators and sub-cent quotes. Only the rule's currency is compared; no FX conversion is performed. A clear current/last-price field takes precedence over historic lows or other amounts. Missing or ambiguous target prices enter the existing retry/pause lifecycle instead of silently counting as no match. Legacy rules infer currency from clear labels or known stock-market URL/symbol clues; unmarked legacy watches keep their original USD behavior, and conflicting clues require an explicit choice. Editing a rule resets its matched baseline. These remain periodic public-page observations, not an exchange realtime feed or a trading-day calendar.

Conversation history opens with the newest 30 user/assistant messages in one snapshot, positioned at the latest message before revealing the transcript. Scrolling up loads older pages using an exclusive message-ID cursor and preserves the reading position; tool results travel with their assistant messages. Historical runs are not replayed through the live runtime on refresh. The app-owned SSE channel continues active replies, and a tail refresh restores their final tool cards. Pagination only limits the displayed history: submitting a turn restores the full persisted context first, including legacy conversations. The current Rich Threads SDK only exposes full-history reads, so the server slices authorized cloud results into pages; client transfer and rendering are paginated. A bounded, owner-scoped 30-second snapshot cache coalesces concurrent reads and shares history between pages and model-context loading; a new local conversation event invalidates it immediately. Initial uncached reads still depend on the upstream full-history response.

Shared sheets and modal dialogs use `ModalOverlay`: a fixed, full-screen blurred backdrop appears immediately, and only the dialog content animates. At 760 CSS pixels and above, all shared sheets (including Bot management/editing, tasks, library, skills, account and model settings) use centered, fully rounded dialogs with desktop spacing, no drag handle and a fixed header above an internally scrolling body. Small and narrow dialogs remain compact; wide content can use 1050 px. Reading views use a large centered dialog up to 1200 px instead of covering the desktop. Dialogs leave at least 24 px above and below them, including in short windows. Below 760 px, sheets keep their bottom entrance and mobile spacing, and reading views remain fullscreen. Bottom sheets start sliding in after a short pause; centered dialogs fade in. The system's reduced-motion preference disables these content animations. Navigation drawers and anchored context menus keep their corresponding navigation/menu interactions.

Web viewports with at least 1024 CSS pixels available use three columns: the Agent list, the conversation and More capabilities. Mouse/pointer or keyboard resizing keeps the left rail within 200–340 px, the right rail within 220–400 px and the conversation at least 520 px wide. Effective maxima tighten with the viewport; widths are remembered locally, and double-clicking a divider restores its default. Narrow web and native layouts use mirrored left/right drawers for the same Agent list and capabilities. A fixed blurred backdrop appears before either drawer slides in; selecting an entry closes the drawer before opening its independent modal. Onboarding continues to mount without these navigation controls.

The top of the capability rail previews the selected watchlist with its total count and first four symbols. Each row shows the name, code/market, percentage change and price; gains use red and losses green. Quotes refresh every minute through the existing batch API. Missing quotes remain dashes rather than falling back to example prices; explicit example mode is labelled. Rows open symbol details, “View all” opens the existing watchlist manager, and “Add to watchlist” opens its search/add form directly (or the create-list form for an account without a list). Both desktop rails and mobile capability drawers share the preview and management state. Capability entries no longer have global/Agent-learned subgroup headings or a pinned explanatory footer. Task records share the single Tasks entry; the duplicate task-history entry is removed. A dashed rounded “Unlock more features” button opens the capability center.

The conversation viewport extends to the top of its column. Agent management floats above it in a centered white capsule with the avatar and a single-line “name · role” label. Narrow layouts retain separate floating buttons for the Agent and capability drawers. The mobile capability drawer has a compact close-only top row, with safe-area-aware top spacing and no duplicate drawer title. Task management is available from the capability rail; the floating task-count pill is removed. The surrounding transparent overlay passes pointer/scroll input through; only the controls intercept it. Scrollable top padding protects the first message while allowing history to pass underneath the controls. Secondary pages retain their own normal header, and onboarding has no workspace controls.

In the Bot conversation, the message viewport also extends to the bottom of the column. The composer floats above it at the existing centered width. An opaque matte base uses the exact chat canvas color and covers the input's lower portion through its bottom margin, avoiding a contrasting footer block while leaving the upper floating edge visible. The base does not intercept pointer/scroll input. Its measured height (including multiline input, attachments, queued messages and the existing keyboard adjustment) determines a measured scrollable bottom clearance, keeping the last message readable above the input even when content is shorter than the viewport. The latest-message control floats above the entire composer stack. Older-message anchors exclude changes to this bottom clearance and wait for their target history page to render before restoring the reading position.

Watchlist modals keep their watchlist/portfolio tabs in local state, so switching tabs never replaces the page underneath; standalone pages continue to use workspace routing. Watchlist action menus use measured trigger coordinates and a transparent outside-click layer, with no extra dimming or blur. They align below the trigger where possible, flip above it near the bottom edge and stay within viewport bounds. Destructive confirmations retain their normal dialog backdrop.

Capability dialogs keep their top plugin, skill, connector and library categories inside the current modal. Selecting the library renders the existing file/insight/note manager locally; its internal tabs remain local too. The selected top category stays highlighted, and switching back to the capability catalog does not change the underlying workspace route. Standalone capability pages retain their normal library navigation.

Application text, controls, fields, navigation, modal content and numeric data use the watchlist's shared Noto Serif SC/Songti serif stack. The app's Text/TextInput foundation supplies this default even when individual styles do not specify a family; explicit code and terminal monospace styles remain semantic overrides. SVG chart labels and product-generated HTML previews use the same family. The capability and watchlist rail headings share 17 px sizing and 600 weight. Web font loading includes weights 400, 500, 600 and 700.

Configured-model pickers combine the current owner's saved personal providers and providers with a server key; personal credentials take precedence for the same provider. Selections are saved per owner and never mutate the deployment's shared `MODEL`. A saved server-provider selection is ignored if its key has been removed. Each provider offers a short curated list, and a hand-written `.env` model stays selectable. Sample and AG-UI backends do not allow personal model connections or model switching. See [personal model connections](USER-MODEL-CONNECTION.md).
