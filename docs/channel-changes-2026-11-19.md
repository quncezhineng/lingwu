上海时间 2026-11-19，在 `8b9f8f6` 已有的发言判断、换组长和四拍之上，又做了两项本地优化。代码分别在：

- `9c6c28af33d058cf6a5b7650a33539c32e9b7a01`：`feat(频道): 圈人后由模型判断是安排组员还是自己回答`
- `789ab24741bd2cc6277a9debee3a269963059764`：`feat(频道): 被圈的组员一起开始研究`

两次都先和当时的 `origin/multi-agnet` 合并过，没有改写已经推送的历史。合并提交是 `7809355` 和 `35e39ec`。远端那两次带进来的是移动端市场、连接管理等别的改动，不是下面这两项的行为。

没有用关键词决定谁说话、要不要安排、要不要换组长。句子里出现「安排、分工、分配、布置、你们几个」不算数。

## 圈人之后先判断是安排还是自己回答

用户消息里 @ 了人，被圈的人仍然先开口。@ 只决定这一轮谁先被问到，不再短路掉「要不要安排组员」。

开口前用被圈名单里的第一位（频道成员顺序）的模型，做一次不带工具的判断。标记是 `MENTION_TURN`。模型只能回答 `ASSIGN` 或 `ANSWER`。`parseMentionIntent` 只认单独一个 `ASSIGN`，其余一律当成 `ANSWER`，包括 `LEAD`、`YES`，也包括原文里的中文。

- `ASSIGN`：走四拍。安排的人是被圈的这一位，不是频道里存着的 `leaderId`，除非他们本来就是同一个人。第一拍先把分工说完并推到可见聊天里，这一拍没有工具，不能自己查行情、搜网页。回复里用 `@名字` 点具体组员。被点到的组员再用工具做自己的那一份，结尾必须 @ 回安排的人。模型漏了，服务端在末尾补「@安排的人 这一份做完了。」每个人有回复或明确失败之后，安排的人再汇总。汇总这一拍也没有工具，不重做分析。
- `ANSWER`：只有被圈到的人说话，可以用工具。单纯让某人分析，不改 `leaderId`。

换组长仍是另一次判断，和这次分工判断分开。只 @ 了一个人、而且这个人还不是组长时，才用现任组长的模型问一次，标记是 `LEADER_ONLY`，只认 `LEAD` 或 `NO`。用户没表达换组长、模型没回答 `LEAD`，就不写 `leaderId`。@ 了两个人或更多，不问换组长。

没 @ 人的路径保持原样：每个成员先做 `RELEVANCE_ONLY`，回答 `ASSIGN`、`ANSWER` 或 `NO`。只有指定组长的 `ASSIGN` 才进入四拍。

## 分工说完后组员一起开始

四拍的第一拍不变：安排的人先把分工说完，工具关掉，聊天里能看见 @ 了谁。名单从这句回复里解析，所以这一拍必须等它结束。

分工说完之后，被圈到的组员不再一个做完再下一个。`speakTogether` 用 `Promise.allSettled` 同时启动每个人的 `work`。一个人的提示只有分工原文和用户原话，不读其他组员正在写或刚写完的内容。同一批开口前会冻住已有回复的快照，后启动的人不会把别人的结果当成自己的上下文。

汇总要等这一批全部结束。谁先写完也不提前总结。回复按组员名单的顺序拼给安排的人，不按谁先落库。失败或没有回复的人记进缺失名单，汇总里点出名字。断线用这一轮原来的那一个 `AbortSignal`：每个正在跑的 `speak` 都会停掉自己的模型调用。已经说出的字仍按原有逻辑落库。断开之后不再补汇总。

没走四拍、但有多个人各自回答时，也是同一套 `speakTogether`，一起开始，不再按成员顺序排队。

界面可以同时显示多个正在说的人。`streamingIds` 记下每一个还在说的成员。文字增量用 `appendMemberDelta` 写回这个人自己的 `live:` 气泡，不会贴到最后一条别人的消息上。同一个人先分工、再总结时，上一条在 `member_done` 时收口，总结另开一条。工具过程仍然收在「工作过程」里，默认折叠。

## 测试

`tests/channel-chat.test.ts` 覆盖：圈了甲且模型返回 `ASSIGN` 时走四拍且组长不变；圈了乙且模型返回 `ANSWER` 时只有乙说话、组长不变；「PCB板块还能延续吗」和「你来当组长」在模型没确认时不换组长。并行一项要求两个组员的 `work` 在对方结束前都已启动，汇总出现在两人都开口之后。气泡一项要求乙的增量留在乙的气泡上，不写进丙的气泡。
