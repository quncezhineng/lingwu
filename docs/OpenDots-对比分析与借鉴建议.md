# OpenDots 对比分析与灵悟借鉴建议

> 更新时间：2026-11-24
> 分析对象：`/Users/luffy/Code/QunCeZhiNeng/OpenDots`
> 对照项目：LingWu（灵悟）

## 1. 先说结论

OpenDots 不是一个投研产品，而是一个很完整的“通用 AI 同事工作台”模板。它最强的地方不在金融能力，而在下面三件事：

1. **把 AI 工作流做成了非常清晰的产品形态**：Dot、Space、Page、Approval、Computer、Slack、Call，用户一眼能懂。
2. **把“草稿 - 审核 - 保存 - 继续编辑”这条文档闭环做顺了**：很适合内容生产、知识沉淀、工作留痕。
3. **把通用能力边界写得很清楚**：什么是本地能力，什么依赖外部服务，什么只是模板，文档与代码口径很一致。

对灵悟来说，它**不值得照搬**，但**很值得借鉴它的产品包装层、文档工作流层、权限可视化层**。

一句话判断：

- **技术深度**：灵悟更强
- **通用工作台体验**：OpenDots 更成熟
- **最值得借鉴**：文档空间、草稿审批、连接器权限表达、Setup/Telemetry 产品化

## 2. OpenDots 的技术架构

## 2.1 架构风格

OpenDots 是一个 **单仓全栈 TypeScript** 项目，偏“单体应用 + 清晰模块边界”：

- 前端：React + Vite
- 后端：Hono
- Agent 运行时：CopilotKit Runtime + AG-UI + TanStack AI
- 持久层：本地 SQLite
- 文档编辑：TipTap
- 测试：Vitest

从代码结构看，它是按领域拆模块，而不是按技术层硬切：

- `src/client`：聊天、Space、Page、Workspace UI
- `src/server`：agent、workspace、computer、connections、pages、voice
- `src/shared`：前后端共享 schema / type / tool contract

这个结构的优点是：**功能边界很清楚，改一个产品能力时不容易满仓库乱跳**。

## 2.2 核心后端骨架

OpenDots 的服务入口在 `src/server/app.ts`，特点很明显：

1. API 安全边界先统一收口：
   - `bodyLimit`
   - host/origin 检查
   - owner token 校验
   - content-type 校验
2. 再按能力挂子路由：
   - `computerRoutes`
   - `connectionRoutes`
   - `workspaceRoutes`
3. 再暴露状态、任务、设置、记忆等基础接口

这说明它的后端设计目标不是“复杂业务编排”，而是**给前端工作台提供稳定的能力网关**。

## 2.3 Agent 架构

`src/server/dot-agent.ts` 体现出 OpenDots 的核心思路：

- 每个 Dot 是一个独立 agent
- 会话上下文与 Dot、Thread、Space 有明确绑定
- 工具权限跟 Dot 配置强关联
- 运行中持续检测设置变化，配置一改就中断当前 run

这套设计非常适合“AI 同事”产品，因为用户能明确理解：

- 这个 Dot 是谁
- 它能做什么
- 它能访问哪些空间
- 它现在在哪条会话里工作

## 2.4 文档与空间模型

OpenDots 的一个亮点是把文档工作流单独建模：

- `Space`：文档空间
- `Page`：空间内文档
- `PageService`：负责 Page 与 Thread 的绑定
- `PageConversation`：围绕某个页面持续对话

这里最有价值的不是“有文档编辑器”，而是：

**文档和会话是双向绑定的。**

也就是：

- 不是“聊完了再手动复制成笔记”
- 而是“这个文档天然就有自己的会话脉络”

这点对灵悟特别有参考价值，因为灵悟现在已经有报告、简报、研究产物，但“产物 - 后续讨论 - 修订版本”的链路还可以更产品化。

## 2.5 连接器与审批模型

OpenDots 的 `connection-routes.ts` 做得很克制，也很值得学：

- 工具默认可启用/禁用
- 只读工具可自动执行
- 非只读工具支持 `Ask first`
- 审批时执行的是“服务端已保存的那次请求”，不是前端临时传的新参数
- 审批有 TTL，只能执行一次

这意味着它把“审批”做成了**可追溯、可恢复、不可篡改参数**的动作，而不是普通前端弹窗确认。

灵悟已经有更强的外部写入审核链路，但 OpenDots 在“连接器粒度的默认安全体验”上更直观。

## 2.6 计算机能力

OpenDots 的 computer 体系特点：

- 每个 Dot 可有自己的 computer
- 权限按 `browser / files / shell` 分开
- Dot 的 token 是从 master token 派生出来的
- profile 与 workspace 文件持久化
- takeover（人工接管）是明确产品能力，不是隐藏调试功能

这套思路偏“每个 AI 同事有自己的桌面/浏览器工作位”。

而灵悟当前更偏：

- 每个 owner 隔离
- agent 可调用浏览器 / computer 工具
- 重心在任务与投研执行，不在“每个角色独占工作位”

所以这部分不建议整体照搬，但它的**权限分层和状态可视化**值得参考。

## 3. OpenDots 的产品功能拆解

如果从产品角度拆，OpenDots 的能力可以分成六层：

1. **AI 同事层**
   - Specialist Dots
   - 每个 Dot 可有角色、说明、工具权限

2. **文档协作层**
   - Spaces / Pages
   - 页面编辑
   - 页面对话
   - conversation 保存成 page

3. **审批层**
   - review before save
   - approve & run
   - 连接器写操作审批

4. **执行层**
   - browser
   - files
   - shell
   - connected apps / MCP

5. **多入口层**
   - Web chat
   - Slack
   - Call / realtime speech

6. **运营与可观测层**
   - setup telemetry
   - runtime telemetry
   - 本地/连接态文档说明

它的真正强项是：**这些层之间衔接得很顺**。

## 4. 灵悟已经领先的地方

这部分很重要，不然容易误判成“OpenDots 比灵悟先进”。

实际上在核心业务和底层可靠性上，灵悟已经明显更深：

### 4.1 投研领域能力更强

灵悟已经具备：

- 市场简报
- 自选股
- 组合与风险分析
- 研究报告
- 价格提醒 / 网页监控
- 论点笔记 / 周检
- 金融数据源接入与降级策略

OpenDots 没有这些垂直能力，它只是一个通用 AI 工作台。

### 4.2 耐久任务系统更强

灵悟已经有：

- SQL 租约
- checkpoint
- 恢复 / 重试 / 取消 / 等待输入 / 等待审批
- 多 Agent DAG 编排
- 事件溯源演进方案

OpenDots 的后台任务能力是够用的，但不如灵悟成熟。

### 4.3 账户与隔离能力更强

灵悟已经支持：

- Supabase 多用户
- JWT session
- 审计日志
- 资源索引
- owner 级隔离
- 个人模型连接

OpenDots 更像单 owner starter template。

### 4.4 移动端产品化更强

灵悟已经有完整 React Native / Expo 产品壳、桌面/移动布局适配、任务中心、能力中心、分享页等，整体更接近真实可上线产品。

## 5. 最值得灵悟借鉴的点

下面按“建议优先级”来讲。

## 5.1 P0：最值得尽快借鉴

### A. 报告/简报的“草稿审批后入库”机制

OpenDots 最值得借鉴的产品动作是：

**先出草稿 -> 用户审核 -> 批准后落成正式页面**

灵悟现在已有：

- 研究报告
- 市场简报
- 外部写入审批

但还可以补一个更通用的“交付物中心”流程：

- 报告先进入 `draft`
- 用户可做轻编辑
- 确认后进入 `approved`
- 再进入 `sent / archived / shareable`

这会明显提升灵悟的“可交付感”，尤其适合：

- 研报
- 晨报
- 组合复盘
- 事件点评

### B. 文档空间化：把产物组织成 Space / Notebook

OpenDots 的 Space/Page 模型很适合迁移成灵悟的：

- 研究主题空间
- 公司/行业研究册
- 周报/简报册
- 组合观察册

灵悟已有文件库和报告，但还可以更进一步，把它们组织成：

- “贵州茅台研究空间”
- “港股互联网观察空间”
- “2026Q4 组合复盘空间”

这样用户会更容易沉淀长期研究，而不是只在聊天里翻历史。

### C. 连接器权限表达更直观：把「只读」说清楚就够了

先核对一下灵悟的现状：

- 连接器目录 [catalog.ts](../apps/server/src/connectors/catalog.ts) 里目前全部是**只读设计**：钉钉 / 文档 / 表格写明「只读」，邮箱「只收信、不发信」，Google Sheets「不改表格」，GitHub 连的是 `readonly` 端点。
- 真正的写操作（发邮件、改日历等）不在连接器里，走的是动作审批链路（`ActionProposal`）。
- 连接器卡片目前展示「名称 + 说明 + 连接状态」，只读信息藏在说明文案里。

也就是说，灵悟的连接器实际只有两种状态：**已连接（只读可用）**、**未连接（不可用）**，并不存在 OpenDots 的 `ask first` 中间态。

所以**不建议照搬 enabled / read-only / ask first 三层权限**，多一层概念，用户多一次理解成本，收益却是零。更好的做法是把表达收成两层：

| 场景 | 前台说法 |
| --- | --- |
| 只读连接器 | 只读 · 不会修改你的账户 |
| 需要写入的动作 | 会先征求你的同意 |

落地只需三个小改动：

1. 连接器卡片统一挂一个「只读」小标签，不再把只读说明埋在介绍文案里。
2. 写入类动作提交前保留现有审批弹层，文案统一为「需要你确认后执行」。
3. 未来真的出现带写能力的连接器，再单独给它标注「会先问你」，而不是现在就给所有连接器加权限设置项。

这样既降低「连接器会不会乱动我账户」的焦虑，又不用引入一套用户根本用不上的权限模型。

## 5.2 P1：值得评估的增强项

### D. 页面级对话绑定

这是 OpenDots 在文档工作流里最有技术美感的一点：

- 一个 Page 对应一个 Thread
- 某个 Dot 围绕这个 Page 持续工作

灵悟可以把它用于：

- 单篇研究报告的继续追问
- 某条投资论点的持续修订
- 某个组合复盘页的后续更新

这样“报告不是一次性产物”，而是“一个持续演化的研究对象”。

### E. Setup 状态产品化

OpenDots 的文档和遥测非常强调：

- 哪些功能只是本地可用
- 哪些需要外部服务
- 哪些是 sample / fixture
- 哪些是真实连接态

灵悟现在文档已经做得不错，但前台也可以进一步把“能力未配置”的状态做得更明确，例如：

- 市场数据已连接
- 浏览器已连接
- 日历未连接
- 电脑未启用
- 推送未配置

让用户在产品内，而不是只在文档里，理解系统状态。

### F. 任务结果与文档结果分层

OpenDots 很清楚地区分：

- 会话
- 任务
- 页面
- Capture / Result Pane

灵悟也可以把“任务执行记录”和“最终交付物”再拉开一点。现在灵悟的执行能力很强，但有时任务过程和最终可阅读产物还可以分层更明显。

## 5.3 P2：可以关注，但不建议现在投入太多

### G. Slack / 多入口触达

OpenDots 支持 Slack 和 Call，这对“AI 同事”产品很加分。

但对灵悟当前阶段，我不建议优先投入，原因很简单：

- 灵悟当前核心价值在投研闭环，不在协同沟通入口
- 先把研究空间、交付物、监控和报告闭环做好，收益更高

除非你后面明确要做“团队投研协作”，否则 Slack 不应排太前。

### H. 每个 Agent 独立电脑

OpenDots 的每 Dot 独立 computer 很酷，但对灵悟不一定划算。

灵悟当前更适合的是：

- owner 级隔离
- 任务级审计
- 共享研究工作区

如果未来频道内多 Agent 真正长期并行，再考虑：

- 为关键角色提供独立 scratch workspace
- 不一定上升到每个 Agent 一台完整 computer

## 6. 不建议照搬的点

### 6.1 不建议照搬“通用 AI 工作台”的产品定位

灵悟的优势来自“投研垂直深度”，不是“做一个更通用的 AI 工作台”。

如果过度借鉴 OpenDots，容易把灵悟做成：

- 功能很多
- 看起来很全能
- 但投研特色被稀释

这是最需要避免的。

### 6.2 不建议为了酷炫而优先上语音/Call

Call 是 OpenDots 很抓眼球的演示功能，但它对灵悟的核心留存未必是最高杠杆。

对个人投资者来说，真正高频的还是：

- 看简报
- 追问标的
- 管理观察和组合
- 接收提醒
- 看交付物

所以语音更适合后续增强，不适合现在当主线。

## 7. 我对灵悟的落地建议

如果把这次分析转成具体动作，我建议灵悟按下面顺序吸收 OpenDots 的优点：

### 第一阶段：补产品层闭环

1. 做“研究空间 / 研究册”模型
2. 做“草稿 - 审核 - 定稿 - 分享”交付流
3. 做更清晰的连接器权限文案与状态页

### 第二阶段：补文档层闭环

1. 报告/简报绑定自己的讨论线程
2. 产物支持持续修订与版本记录
3. 从“文件库”升级为“研究资产库”

### 第三阶段：补协同入口

1. 若后续有团队场景，再评估 Slack / channel
2. 若后续强调陪伴式使用，再评估语音

## 8. 最后一句判断

OpenDots 最值得灵悟学习的，不是“它能连 Slack、能打电话、能跑电脑”，而是：

**它把 AI 工作过程包装成了用户能看懂、敢使用、愿意持续沉淀的产品形态。**

灵悟下一步最应该借鉴的，就是这层“工作台产品化能力”，然后继续把自己的投研深度优势放大。
